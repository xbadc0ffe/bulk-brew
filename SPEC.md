# Bulk Brew: Project Spec

Source of truth for scope, data, and architecture. Describes what exists and what is decided, not how it came to be. Update it when a decision changes.

## Purpose

Turn a large pool of bulk Magic: The Gathering cards into playable casual decks. The user imports a card list into a pool, picks a deck size, colors, and optional styles (or a commander for 100 cards), and the app builds several deck options from what is available, ranked by strength and fit. Accepting a deck saves it and takes its cards out of the pool, so the next build uses what is left. The app calls the pool the Bulk List.

Bulk Brew presents itself as a bulk builder: it makes good decks from what a pile holds. Real decks deserve a person's care; the app does not try to replace that.

The app is self-sufficient: no language model calls at runtime, no developer server, no user data sent anywhere. All judgment lives in data (card facts, tags, config) and a deterministic builder.

Targets: a static client-side web app and an iOS app, built together on one core. Free, open source (MIT).

## Principles

- **Deterministic.** Same pool, settings, config version, and data version give the same deck.
- **Logic as code, judgment as data.** Templates, archetypes, synergy rules, land rules, and weights live in versioned config files so they can be tuned without code changes and shipped to iOS without an App Store release.
- **One core, two shells.** Parser, name resolution, pool, archetype scan, builder, and export live in a platform-free core. The web app and the mobile app are separate interfaces with different layouts on the same core.
- **Deckbuilding is not "lands plus spells".** A deck is a curve, a type mix, role coverage, synergy, and a mana base sized to the spells it holds.
- **Explainable.** Every card in a built deck records why it is there.

## Product

### Deck sizes

| Size | Style               | Notes                                                                                                                                                            |
| ---- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 100  | Commander           | One commander plus 99, singleton (basics exempt). Colors come from the commander. Phase 13.                                                                      |
| 60   | Constructed, casual | Max 4 copies of a card by default.                                                                                                                               |
| 40   | Limited-style       | Max 4 copies by default.                                                                                                                                         |
| 20   | Jumpstart style     | Shown as "20" with a note when selected. Includes its lands. Max 2 copies by default. Any two packets of different colors shuffle into a two-color 40-card deck. |

### Colors

Decks use one to five colors. Mono-color stays the builder's strongest mode; every added color makes a deck harder to build well, and the app says so rather than refusing.

A color gives access to its cards, not a share of the deck. The builder takes the cards that best serve the style from any of the colors and does not aim for an even split: the deck leans on its main color, the other colors bring what they add, and at 60, 40, and 20 a picked color may be left out entirely (options try every subset). The only floor is a few spells per color (`minCardsPerColor`), so a deck named for a color holds some of it. A color the pool holds fewer spells of is a light splash, as real draft decks splash one or two cards: its cards join only on their own merit. A deck that ends up without a picked color is named for the colors it uses. A Commander deck must stay inside its commander's colors but need not use them evenly. For example, from the owner's 5,300-card test lists a Black-Green deck came out 19 black and 14 green spells, and a Black-Red-Green commander deck 26, 19, and 14.

- **60, 40, 20**: a card is a candidate when every mana symbol in its costs and rules text can be paid by the deck's colors (hybrid symbols when either half fits), so hybrid cards work in mono decks. Colorless cards are always eligible. Phase 10.
- **100**: candidates are cards whose color identity fits inside the commander's, as the format requires.
- Multi-color decks have a main color (may hold double pips), secondary colors (single pips), and optionally a light splash (a few single-pip cards costing three or more). Colored source counts per color come from a probability target in config: the chance to cast each spell on curve given the land drops were made, met for a share of the color's spell copies per size (`landRules.colors.sourceCover`, fitted on the reference corpus's train split so the median real multi-color deck from 2015 on falls short in none of its colors, the commander counted among its spells; `npm run sources:fit`).
- Two-color play also comes from pairing two 20-card packets; pairing stays as a mode.

### Pool flow

1. **Import** decklist text or a collection CSV (ManaBox, Moxfield, Deckbox, or any CSV with name and quantity columns), pasted or from a file. Import is a subpage of the Bulk List. The text is checked live as it is typed: matched cards and colors, and each unmatched line, which can be renamed, swapped for a suggestion, or skipped. Import adds the matched cards to the pool; lines that did not match stay in the box.
2. **Pool** is the single active set of available cards, keyed by oracle id with quantities. It persists on the device between sessions and can be exported and restored from Settings (see Settings).
3. **Build** from the pool. The Build page shows deck options ranked by strength (see Build options); opening one shows the full decklist with an explanation.
4. **Accept** (after a confirmation) saves the deck and takes its cards out of the pool (the `committed` flag). **Reject** drops the result and returns to the form with every choice kept. **Export** copies or downloads the list. A result survives moving between screens until it is accepted or rejected. Before Accept, any card of the result but the commander and basics can be **replaced** from its card detail, a nonbasic land also by a basic (see Decisions); Accept saves the deck with the swaps; Back, Build in the sidebar, and opening another deck from Analyze ask before they drop them.
5. **Build again** from what is left, until the pool runs out of a color.
6. **Remove cards** with Select on the Bulk List; Settings clears everything. A saved deck's **Remove** asks how: **Delete** leaves the pool as it is, **Disassemble** returns the deck's cards to the pool and then deletes it, and a deck whose cards never left the pool only offers Delete. Clicking a deck's name renames it, on the deck list or the deck page. Accepting is refused, with a count, when the pool no longer holds all of the deck's cards.
7. **Pair** two 20-card packets of different colors from a packet's view: a what-if preview of the combined 40-card deck, and **Merge**, which replaces both packets with one deck (packets still in the pool are taken out of it first).

Basic lands are unlimited by default and need not be imported; imported basics are kept as pasted. The Infinite basics switch lives on the Build form. Nonbasic lands are always tracked.

The Bulk List filters by color, type, subtype, mana value (a comparison and a value), short tags, and subtags, sorts by any column, can select several cards to remove at once, and can open the pool analysis under the list (see Analyze pane). Short tags ("Removal", "Draw", "+1/+1") come from `config/display-tags.json`; subtags are the config's role and style labels; the card detail also lists the raw Scryfall tags. A card detail opened from a deck shows only the roles, styles, and the short tags they give that the card earns in that deck, by the card needs reader against the deck's supply (`packages/core/src/deck-credits.ts`); the Bulk List shows them all.

### Settings

Defaults live in `config/settings.defaults.json`.

- Max copies per card, per deck size (60: 4, 40: 4, 20: 2), set on the Build form under the deck size; Settings does not list them. 100 is always singleton: the stepper stays on the form, held at 1.
- Infinite basics (on), set on the Build form.
- Rarities the builder may use (all four by default), set on the Build form. Basic lands and cards with no known rarity are never filtered out.
- Include Un-set and acorn cards (off).
- Show card art (off on first launch, remembered).
- Export (web): asks Mass export (Bulk list, Decks, Both, or Cancel), then Export as JSON or TXT. JSON is a backup file; Both is a full backup with the settings. TXT is plain card lists, the bulk list under a `// Bulk list` heading and each deck as its decklist, with comment headings so it imports back as a card list (`collectionText`).
- Restore from backup (web): asks Bulk list, Decks, or Both, then opens the file picker for a JSON backup, then confirms what it replaces. Each part replaces only itself; Both also restores the settings when the file has them. A file without the chosen part is refused with a message. A backup holds any of its parts (`pool`, `decks`, `settings`), so a bulk list or deck export restores like a full one. The phone app still exports and restores everything.
- Appearance: light, dark, or system, and a theme color (grey or one of the five colors). The app icon in the web sidebar and browser tab follows the mode. This is a device preference kept in `localStorage` so it applies before first paint; it is not part of `Settings` and not in backups.

### Platforms

- **Web app**: desktop-first, fully static, hosted on GitHub Pages. Works offline after first load.
- **Mobile app**: phone and tablet layouts, developed in a browser, shipped to iOS through Capacitor. Bundles the data pack and config, and can update both over the air.

## Data

### Sources

Scryfall bulk data, downloaded by `scripts/fetch-scryfall-bulk.mjs` into the gitignored `data/raw/`:

- `oracle_cards`: one entry per unique card (oracle id), with the default printing's image id.
- `oracle_tags`: Scryfall Tagger function and synergy tags. About 4,600 tags, 240,000 taggings, 36,000 tagged cards. Tags form a tree through `parent_ids`. Tagging weights are flat in practice (99.7% are "median"), so tags are treated as boolean and any weighting comes from config.
- `rulings`: development reference only. Never bundled. If a card detail view ever shows rulings, they load from Scryfall on demand.

- `default_cards`: one entry per printing, read only to find each card's lowest rarity across its paper printings. Nothing per printing is shipped.

Not used: all cards, unique artwork, art tags. Imports resolve by name against oracle cards.

A local tag overlay in `config/tag-overlay.json` fixes and gap-fills tags at pipeline time.

### Card identity

Everything is keyed on `oracle_id`. Printings, sets, collector numbers, finishes, and languages are ignored for card facts and building. A set code and collector number from an import line are kept only as an art hint on the pool entry.

Name resolution handles full multi-face names ("A // B"), front-face-only names, case, accents, punctuation, and the flavor names some printings carry (see Data pack below). Where one name maps to several oracle ids, the non-Un-set card wins; a name that belongs to a card never falls through to another card's flavor name.

### Data pack

The shipped database is one compact JSON file, gzip-compressed by the host. Shape: `DataPack` in `packages/core/src/types.ts`. Per card: oracle id, name, layout, mana cost, mana value, type line, oracle text, colors, color identity, keywords, power, toughness, loyalty, produced mana, normalized types, derived `entersTapped` and `unset` flags, tags, faces, and the default printing's image id. The 2026-11-02 pack holds 34,168 cards: 23 MB raw, 5.4 MB compressed.

Schema 2 (phase 9) adds Commander legality (banned or not legal), the Game Changer flag, Scryfall's popularity rank (one signal in the card strength score), and rarity. Rarity is the lowest rarity among the card's paper printings, the way rarity-based formats count it (special and bonus stored as rare); when the printings file is missing, the default printing's rarity stands in. The core reads schema 1 and 2 during the move, treating the new fields as absent in schema 1. Decks record `CardIndex.dataVersion`, the pack date plus the schema from 2 on, so packs of different schemas never share a data version. Cards also carry the flavor names some printings show in place of the card's name (Universes Beyond, Godzilla, and similar; "Bartz Klauser" is Winota, Joiner of Forces), read from the same printings file, so lists exported with those names import. A real card name always wins over a flavor name. The field is optional and older readers ignore it, so it needed no new schema.

The pack is served under one fixed name, `data/cards.json`, and the service worker answers from its cache first. So every release of the core must read the previous schema as well as the current one: a returning user may load the old cached pack once before the new one arrives.

JSON was chosen over SQLite because the data is small, loads with one fetch, needs no WebAssembly on the web, and decodes natively in Swift if the iOS app ever goes native.

### Filters and edge cases

- Exclude non-playable layouts (tokens, emblems, art series, planes, schemes, vanguards, and similar), oversized cards, and Alchemy digital-only designs. The oracle file lists one printing per card and sometimes picks a digital printing of a real paper card, so a printing's paper flag is not used as a filter.
- Un-set and acorn cards stay in the pack flagged `unset` and are excluded by default.
- Multi-face cards: a modal double-faced card with a land face counts as both a land and a spell; split and adventure cards carry multiple costs; transforming cards use the front face for cost and color.
- Card art for cards printed on two sides (Scryfall's transform and modal double-faced layouts, `hasBackImage`) shows the front with a round turn-over button over the right edge of the art, halfway down (the owner's call; it sits away from the artist credit and copyright line, and the image itself is never changed); it shows the back image (`/back/` on the image host, `face=back` for a printing). The card detail, the commander tiles, and the replace picker's large card have it; list thumbnails show the front. Clicking the art in the card detail or the picked commander's pane opens it full screen (Scryfall's large image, as tall as the window allows), with the same button. It opens at 75% of the size that fills the window's height and zooms from 50% to 400% (the largest image blurs past that) with the mouse wheel around the pointer, the + and − buttons at the bottom or the + and - keys, or a two-finger pinch; the percentage (or 0) returns it to 75%, and dragging moves a zoomed card within the window (`packages/ui/src/data/zoom.ts`). Escape, the close button, or a click outside closes it.
- X spells, hybrid, and Phyrexian mana are handled in mana value and castability logic.

### Pipeline

`npm run data:build` runs `packages/pipeline` under Node 24:

1. Read the raw bulk files.
2. Filter, trim, normalize, derive fields.
3. Join Tagger tags and the local overlay.
4. Write `data/packs/cards.json`, its gzip (the release asset, named with the schema, such as `cards.v2.json.gz`), and `data/packs/manifest.json` (version, URL, checksum, size, card count), and copy the pack into each app's `public/data/` for local development.

Tests cover the edge cases above with fixture cards.

### Learned data

`npm run learn:build` (`packages/pipeline/src/learn-build.ts`) learns from real decks: the reference corpus's train split (never the owner's local lists), EDHREC's pages (cached by `npm run edhrec:fetch`), and Commander Spellbook's combo file (`npm run spellbook:fetch`). Everything it writes is aggregate, rounded numbers keyed by oracle id, tag, or style.

- **Tag and style level**, bundled with the config in `config/learned/` (about 100 KB): each style's profile per size (the median and middle half of its real decks' theme enablers and payoffs, roles, curve, and card types, as shares of their spells, plus lands), each style's theme share in random bulk by color class, tribes' shares the same way, the tags each style's decks play more than real decks in general, and tag pairs real decks hold together more often than chance. Versions are hashes of the content and join `configVersion()`.
- **Card level**, `data/learned.json` (committed, about 2 MB): per-card plan fit (EDHREC theme lift and corpus lift), for each commander EDHREC covers the plans its decks run and the cards they play more than decks of their colors, card pairs from draft decks of one set and color pair, and combos (three cards or fewer, no template requirements, a standalone result from the list in `builder-weights.json`, pinned by the Spellbook file's timestamp). The apps load it beside the card data and attach it to the card index; the core treats it as optional, so a missing or broken file falls back to the tag level. Decks record its version as `learnedVersion`.

### Publishing and updates

- Raw bulk files and built packs are never committed. The repo pins `data/manifest.json`.
- A weekly GitHub Actions workflow fetches the bulk files, rebuilds the pack, and when the data date changed, publishes the pack as a release asset tagged `data-YYYY-MM-DD`, commits the manifest bump to main, and triggers the web deploy.
- The web deploy downloads the pinned pack with `npm run data:pull`, verifies its checksum, and serves it from the site's own origin as `data/cards.json`, compressed in transit by the host. The browser caches it; a new deploy brings the new pack. `data:pull` and `data:build` also install the committed `data/learned.json` as `data/learned.json`, cached the same way.
- The iOS app bundles the pack and config at build time and offers "check for card updates", which downloads a newer pack and config from GitHub. Apple permits data updates; code changes still need an App Store release. No user data is sent.

## Images

- One default image per card, the printing Scryfall's oracle file chose. The pack stores the printing id; `imageUrl()` builds the URL.
- Images load on demand from Scryfall's image host, directly from the user's device, and are cached there. Only cards in the pool and in decks are ever loaded, and nothing is requested while the art setting is off.
- When an import line carried a set code (and collector number), the pool entry keeps it and the card detail shows that printing, falling back to the default image and then to text. List thumbnails use the default image. Set codes affect nothing else.
- Card art is off by default. Everything works as text without images.
- Images are never cropped, distorted, recolored, or watermarked.
- A "download images for my pool" action for full offline use is a later version.

## Config

Versioned data files in `config/`, typed and validated by `packages/core/src/config.ts`. See `config/README.md` for the file list. In short: deck templates per size (land formula constants, default curve profile, type mix, role quotas, tolerances), curve profiles, role definitions as matchers over Tagger tags, keywords, types, and derived facts, synergy and composition archetypes, synergy rules, land rules, builder weights, settings defaults, and the tag overlay. Initial values come from the guides in `docs/guides/`, which the user reviews. `npm run config:check` validates the bundle against the data pack.

## Archetype scan

Scan the pool and report, per color set and per deck size, which archetypes are viable, with enabler and payoff counts (synergy archetypes) or role and curve counts (composition archetypes), plus how close near-misses are. The builder uses the scan as its seed step and the Build screen shows it to guide the style choice.

A deck is possible when the pool has enough spells for the slots left at the template's most lands (`minSpells`; the builder pads a thin deck with lands up to the clamp) and, at 60, 40, and 20, at least half of the base spell slots can be cards of the deck colors (`MIN_COLORED_SHARE`); colorless cards fit every color but cannot make a color's deck on their own. A multi-color deck at those sizes needs at least one spell of each of its colors; a color below `minCardsPerColor` is a splash. At 100 the commander's identity sets the colors, so neither color check applies. Cards with a {C} pip are excluded, since basics cannot pay for them. Every theme card counts toward viability; only theme cards at or above the card strength bar (`themeMinStrength`) count toward the margin, so a theme made of weak cards ranks low without being ruled out. The theme rules' viability (`rules`, from `growViability`) counts a theme card only when the pool could meet its needs and its drawbacks (a pool-level supply over the request's candidates, lands included; nothing is taken as met, so an Equipment payoff counts in no pool without Equipment), and the plain shapes' role counts only cards that could earn the role in that pool; Lo and Li's Noble and Lesson jobs count in no pool without Nobles or Lessons. At every size `rules` is the one field the apps read, on every style: its `viable` is false when the size cannot be built (`possible`), its `floors` are the pool's counts for the floor alternative it meets best, exactly as the builder counts the pool, and a plain shape is viable wherever the size can be built, as best fit always plans it. At 100 the scan runs under the commander (`scanPool(..., commander)`): it leads rather than counting as one of the 99, and its own theme job counts once (`grow.commanderCredit`), as the builder counts it. The old fields (`viable`, enabler and payoff counts from the `archetypes.json` matchers) stay for the classic paths: secondary styles and tribes. The Build screen shows colored counts on the color buttons and the reason a color is unavailable. `npm run review:agree` (and a test on fixtures) checks that the scan, the Analyze pane's plan, the Build page's plan, and the builder list the same styles with the same pool counts, and that each deck shows what its builder counted; it prints counts and style ids only, so it can run on held-out pools.

## Builder

### Inputs

Pool, deck size, colors, optional primary and secondary style, commander (100 only), settings, config version, data version.

### Steps

1. **Candidates**: pool cards that fit the colors (see Colors), honoring the Un-set setting and copy limits, and excluding cards with a {C} pip and, at 20 cards, spells a packet cannot cast (see Jumpstart packets). Guidelines from `docs/guides/` (2 copies of legendary and six-plus cards, type caps, the theme strength bar) shape the passes but bend in the last filler passes when the pool runs out of other cards. Magic rules and the user's settings (copy limit, colors, rarities) never bend.
2. **Archetype**: at every size without a secondary style, the grow builder's plan picker (see "Plan picker" below): best fit builds every plan the request can build, the three plain shapes, each theme the rules call viable, and under a commander the tribes it names, and keeps the finished deck with the highest picker score. The rest of this step describes the classic builder, which still builds secondary styles and tribes (`explanation.builder` says which ran); only secondary styles read the learned plan data. Where best fit's plans reach the classic builder (a tribe the commander names, or at 60, 40, and 100 a plain shape a thin pool cannot fill or best fit's last resort; a 20-card packet pads with lands instead), it runs without the learned plans, tags, and card data (`withoutLearned`), and so does a tribe asked for by name at 100 without a secondary style, so its option is best fit's deck card for card. The preferred style if viable. At 100, 60, and 20 (`builderWeights.learned.plan[size].use`; only a request with a secondary style and no primary style, which the apps never send, reaches it now), best fit picks the plan the pool leans to (`packages/core/src/plan.ts`): each viable theme scores by how often real decks of the size run it (and, under a commander, how often the commander's EDHREC decks do, and how its own text pulls), how much more of its theme the pool holds than random bulk of the same colors would, and whether the pool can fill it to what real decks play; each plain shape scores by how close the curve of the pool's strongest cards is to its own. A weight per plan, calibrated by `npm run learn:build` on the corpus train split, makes each plan come up about as often as real decks run it, so a theme made of common cards does not win by default and a pool with nothing unusual builds a plain shape, as most real decks without a theme are. Best fit builds the three best themes and the viable shapes and keeps the best plan; the deck score only breaks ties. Under a commander, best fit also tries the tribes the commander names. Without the learned data, best fit builds every viable style and keeps the highest deck score, the styles the commander rewards getting up to `commander.styleBonus`.
3. **Reserve lands**: start from the template's base land count so the spell count is known.
4. **Fill spells** in passes with per-type caps so no category floods the deck: role minimums, theme enablers and payoffs to their minimums, each color's minimum (multi-color), role targets, the theme toward the median of real decks of its plan (learned), type mix minimums, curve fill toward the profile, then filler. Multi-color decks first pick a main color and mark weak colors as splashes; spells that ask a lot of a secondary or splash color lose strength points while picking (see `docs/guides/mana-base.md`). The last filler pass ignores type caps so a creature-only pool still fills the deck.
5. **Size the mana base** from the spells actually chosen: a base count per size, raised by average mana value, lowered per cheap mana source, clamped to a range. Credits per source kind and cost are in the template; dorks earn slightly less than rocks because they die to removal, and dorks still count as creatures in the curve. If the land count moved, trim the least important picks or re-fill, until the count is stable.
6. **Improve** with bounded local search: swap a chosen card for an unchosen candidate when the objective improves, then re-fit the land count again. A swap may not take the primary or the secondary style below the minimums its fill reached.
7. **Nonbasics and basics** per land rules. A one-color deck scores each nonbasic against the basic it would replace and takes it only when it is better: making the deck's color or any color gains nothing, entering tapped, paying life, a drawback, or making no deck color all cost, and a utility ability counts only on a land of the deck's colors that costs nothing against a basic, or when a lasting ability (not a one-time trigger on entering) serves the deck's style (`landRules.mono`). In one color, utility holds only when the card needs reader finds the ability earned in the deck: its needs met by the deck's spells (Trenzalore Clocktower's needs a Time Lord, Okina's a legendary creature); the no-cost credit also counts what the land does as it enters and what a mana ability does beyond its mana (Arena of Glory's haste), the plan credit only a lasting ability. The multi-color utility point still reads the tag alone. A land never meets its own entry condition. How a land enters is read by the card needs reader too (`landEntryReading`): "enters tapped unless you control a Swamp", "you may reveal a Forest card", "unless you control a legendary creature" or "a planeswalker" as the resources they name, met by the deck's colors and spells (a tribe style counts for its type, a commander for a legendary creature); land counts, low life, and "pay 2 life" as game state. `landEntry` turns that into a chance to enter tapped with the land rules' weights (`landRules.entering`); the multi-color score and tapped cap use the same reading, and "Activate only if ..." mana conditions are the reader's conditions held against the deck as well (a condition on game state alone, such as Mirrex's "this land entered this turn", is no steady source; the basic-land duals' "or if you control a basic land" asks for nothing). Lands whose mana depends on a draft never enter a mana base. Multi-color decks size each color's sources from what its spells need to cast on curve and split the basics to match: first to the colors below their want, then below what all of a color's copies need, then by colored pips.
8. **Validate**: exact size, copy limits, color identity, land count inside the clamp.

Constants live in `config/deck-templates.json` and are explained in `docs/guides/deck-shapes.md`.

### Objective

At every size the plan picker's score ranks plans (see "Plan picker"); the rest of this section is the classic builder's objective (secondary styles, tribes). Template fit (curve deviation, type mix, role quotas, with minimums weighing more than targets) plus synergy density, scaled by the chosen archetype's synergy weight. With the learned plans, each copy a role or card type sits outside the middle half of real decks of the plan (and each theme card above it) costs `learned.profileWeight`, so each plan keeps its own shape, and a swap may not take the theme below the target its fill aimed for. Cards are then chosen by what they add to the plan beyond their strength (`packages/core/src/select.ts`, weights per size in `learned.selection`): their fit to it (how much more its real decks play the card's tags and the card, and at 100 how much more the commander's EDHREC decks play it), their pairs with the cards already chosen (tag pairs learned from real decks and card pairs from draft decks), and Commander Spellbook combos the deck can complete, weighed by bracket and counted fully at 100 and less at 60, 40, and 20. The hand-written synergy rules then count at a quarter, for cards the data does not cover. The same value orders the candidates in every fill pass. Candidate ordering first prefers cards that fill a curve bucket still below target, then follows the tiebreak list in `builder-weights.json`, then card id.

Phase 9 adds a **card strength score** and a **deck score**. Card strength is computed from card data with weights in config: an effect on a body beats a vanilla body, broad and instant-speed removal beats narrow removal, fewer colored pips is better, value on entering or dying and protection keywords count, buff-only auras and equipment count little outside their theme, and Scryfall's popularity rank adds a signal. It joins the objective and replaces stats per mana as the main tiebreak. The deck score is led by synergy density (0.6), with card strength, role coverage, curve fit, type mix, and (multi-color) castability as minor tiebreaks, because those cannot see how well cards work together. It ranks archetypes for best fit and options on the Build page. At the sizes that build with the learned plans (100, 60, and 20), the deck score is instead how close the finished deck sits to real decks of its plan (the same profile distance `corpus:eval` measures: theme enablers and payoffs, roles, curve, and card types), at 0.7, with card strength and castability at 0.15 each (`deckScore.learned`); it ranks the Build page options and the Analyze pane. Over corpus pools, the first option the Build page shows now sits much closer to real decks of its plan (distance 0.86 to 0.38 at 60, 0.80 to 0.38 at 20, 0.57 to 0.31 at 100) and no longer leans to Tokens and Aristocrats at 60 (95% of first options before). A theme is measured against its own decks and a shape secondary against the shape's, with the theme features' spread floored as `corpus:eval` floors it. Best fit adds `learned.plan[size].deckScoreWeight` of it to the plan score: 0.01 at 20, where builds moved closer to real decks with plan recall flat and the blind review favored them 7 to 3; 0 at 100 (it cost plan recall) and 60 (the review favored the builds without it).

### Output

A deck with cards grouped by type, basics by color, and a `BuildExplanation`: archetype, the builder that ran (`builder`: grow at every size, classic for secondary styles and tribes, or for a plain shape the grow builder cannot fill on a thin pool at 60, 40, or 100), the plan picker's score and its parts (`pick`, internal, with every plan best fit compared), curve, role counts against targets, land reasoning, key synergies, notes. The Roles bars on screen also count the deck's theme cards, in the words of the builder that made it (`deckStyleRows`, `packages/core/src/deck-themes.ts`). A grow deck's theme reads the theme rules: each floor of the alternative it was built to, which the explanation records with the builder's own count (`explanation.theme`), such as "Voltron setup cards 13/12" and "Voltron payoff cards 5/4", counted again from the saved deck: each card's job once, only where the deck earns it, the commander once. Its "Setup: ..." and "Payoff: ..." reasons show only when the card earns that side in the deck, Replace lists the same jobs, and its key synergies are the rules' themes the deck earns both setup and payoff for ("Tokens: 10 setup cards, 6 payoff cards"). A grow deck carries no classic deck score. A classic deck (secondary styles, tribes, and 20-card packets saved before builder phase 2 step 5) shows the enablers and payoffs of the `archetypes.json` matchers against their minimums (`styleCounts`), a theme card counting only when it earns that side in the deck, a tribe's cards as they are, and the synergy rules' lines. The role bars likewise count each spell under the roles it earns in the deck (`deckRoleCounts`), against the targets the build recorded; the explanation keeps the builder's own count. Each card also carries provenance (which role or synergy slot it filled, or filler), shown as "why this card" in the deck view and used for debugging; a reason that names a role or theme side the card does not earn in its deck is left out.

### Modes

- **Best cards**: each build takes the best available cards from the current pool.
- **Batch balanced** (later): several decks from one pool, holding back the stronger deck until deck-level scores are within tolerance.

### Seed and grow (phase 15) and the plan picker (builder phase 2)

At every size (20, 40, 60, and 100 cards) every request without a secondary style or a tribe goes to the second builder: seed and grow (`packages/core/src/grow.ts`, the review's prototype `b-grow`, see `docs/review/proto-b.md` and `docs/review/report.md`). It reads the theme rules in `config/theme-rules.json`: for each themed style, setup jobs and payoff jobs over oracle text, type lines, tags, and keywords, each card counted once as the job it mostly does, a rider (surveil 1 on a removal spell) counted as nothing, repeatable setup weighing about twice a one-shot, and floors per size that a decent deck of the style needs (`docs/review/theme-rules.md`). The steps: pick the floor alternative the pool meets best; seed payoffs up to the payoff floor, each pick by how much of the floor it closes, its quality among cards of the same mana value and kind, and room on the curve; grow setup to the demand the seeded payoffs create (and repeatable setup toward a floor of repeatable setup or payoffs, Burn's, when payoffs leave it short, as the scan counts both); fill roles to their minimums and the curve slot by slot behind a payoff gate (a payoff of the plan enters only when the deck's setup covers it; a payoff of another style needs that style's setup in the deck; setup of a style flagged `setupNeedsPayoff`, such as cards that mill the opponent, needs that style's payoffs); then the land count and mana base as the classic builder sizes them. Aggro, Midrange, and Control build as plain shapes of the same steps; a plain shape takes creatures first to the middle of its creature range (`grow.creatureFill`), so Control holds the ground with about 14 creatures at 60 instead of 10. A payoff of the plan the setup already covers keeps a pull in the fills above the payoff floor (`grow.payoffPull`), as setup does above its floor, and a creature whose payoff job for another style needs nothing (a flying carrier for Voltron, a big body for Ramp) is not held back as an off-plan payoff. The commander counts once toward its theme job. The constants live in `builderWeights.grow`.

A credit holds only in a deck that supplies what it depends on (builder phase 2, step 2). The card needs reader (`packages/core/src/card-needs.ts`, `config/card-needs.json`) reads each card's text into what every ability depends on; the grow builder keeps a running supply of the deck it is building and gates every pick beside the payoff gate: a card fills a role slot only on a role it earns, and a theme slot only on a theme job whose needs the deck meets, the theme's own resources aside (its floors count them: a lifegain payoff goes in before the lifegain, `themeResources`); when that leaves the theme core short of its floors because a payoff's needs come from cards the fill adds later (ten creatures for a reanimation trigger), a second try takes each job the pool could pay for. A card with a drawback the deck does not meet (Tragedy Feaster without lifegain) or with credits of which it earns none is left out, except as the last relaxation of a thin pool's curve fill. Picks are scored on what the pool can pay for: strength drops the effects no deck from the pool earns (Yathan Tombguard's repeatable card advantage in a pool without counters), and an "or pay {N}" card is priced, cast, and slotted at its mana value with the mana paid when the pool lacks the resource (Caustic Exhale is a two-drop without Dragons). The commander's own jobs and roles count only while the deck meets its needs. The finished deck, lands included, is checked once more. A theme card whose job the pool pays for but the deck does not (the theme core's second try counts the pool's supply) is fed first: for each unmet need of its job and each unmet gate (a drawback, a required cost such as a Goblin to sacrifice), the best pool card that supplies it (more copies of the card itself when it supplies its own) takes the place of a curve copy (other plans' cards first, the weakest first) or of a card picked for a role the deck holds above its minimum, never a supplier of any of the card's needs or one another card's needs hold on; kept only when the card then earns its job and the floors are no worse (`feedNeeds`). The theme core's loose try takes a plan card on its job without checking its drawbacks against the cards picked so far, as the scan's pool count does (Frightcrawler's threshold, which a finished Voltron deck meets); the finished-deck check holds it to them. Otherwise: a copy the deck does not support, or whose recorded reason it does not earn, goes for the best card for the same slot (the same role or theme side, else its curve slot; never the copy's own card), keeping the deck's size and land count, a few rounds at most. A role card the deck still supports whose role no other card can fill stays as a curve card; any other copy with nothing better stays as it is and counts as unsupported. Then the plan's floors are counted as the finished deck earns them, nothing taken as met: a theme the deck cannot pay for is short, and the request gets the nearest deck and its note, never "minimums met". The explanation's role counts and each card's reason record only earned credits. `npm run needs:decks` counts unsupported cards per deck over the eval and development pools; `npm run eval` reports them per size.

When the player asks for a style (`requireStyle`) and it misses its floors, the builder answers with the nearest deck it can build and a note (`explanation.nearest`, also in the notes): the first style in the rules' `kin` list for it (styles that share the resource) that is viable, else best fit, which never holds the short style. The deck is named for what it is. A style without `requireStyle` is one plan of a list (a Build page option, an Analyze deck): built as best fit would build it, or refused with what the pool lacks so the list drops it. Secondary styles and tribes keep the classic builder; `explanation.builder` records which one ran, and at 60, 40, and 100 a plain shape the grow builder cannot fill on a thin pool comes from the classic builder too. A 20-card packet never reaches the classic builder without a secondary style: a thin pool pads it with lands up to the template's range, as the scan counts the size buildable, and a request no plan fills is refused. The scan reports the rules' viability per themed style (`rules` on each synergy report: viable, margin, and what the pool lacks in plain words) and both apps list styles from it: Viable, or Short (pickable, answered with the note and the nearest deck) down to `grow.nearMargin` of the floors. `config/theme-bulk.json`, written by `npm run theme:bulk` after a rules edit or a new data pack, is the bulk baseline (each style's expected setup and payoff per color class over every common and uncommon) that the plan picker reads; nothing computes it on the device.

**Plan picker** (builder phase 2, step 3, `pickScore` in `grow.ts`, constants in `builderWeights.picker` and `grow`). One score ranks the finished deck of every plan, whatever built it, and the same number orders best fit, the Build page's options, and the Analyze pane, so the first option is the best fit card for card. The plans are the three plain shapes (always, so a pool where no theme is viable still has options), each theme the rules call viable, and under a commander each tribe it names that the pool supports (built by the classic builder, scored the same way). The score is the product of:

- **Quality**: each spell against the pool's cards of the same mana value and kind (creature or not), rank for rank: the deck's best two-drop creature against the pool's best, its tenth against the pool's tenth (a copy beyond the pool's usual copies against the slot's last). A deck that plays the best cards of each slot it uses scores 1 however many it needs, so an Aggro deck's dozen cheap creatures cost it nothing (the prototype compared every copy with the slot's top five, which kept Aggro out of best fit), while a weak card a plan forces in over better ones of its slot costs it. Among plain shapes it is near 1 by design, so fit and the mana tell them apart.
- **Fit**: the share of the shape's role minimums, curve slots within the template's tolerance, and the creature count its fill aims for, that the finished deck reaches, roles counted only where earned. Role targets stay out: the fill builds to the minimums, and a shape with small targets (Aggro's at 40) would reach them more easily than one with large ones.
- **Clean**: the share of spell copies the deck supports (card needs; normally all).
- **Cast**: the share of the spells (commander included) the deck's mana casts on curve, from the sources it records per color (1 in one color), to the power `picker.castWeight`. Quality is measured within one color set's own pool, so this is what keeps a deck of more colors from ranking above a one-color deck of as good cards in the Analyze pane and among the options of several picked colors.
- **Colors**: quality, fit, depth, and margin are measured within the color set's own pool, which grows with every color the set adds, so across color sets each color past the first costs `picker.colorCost` (0.1) of the score, as "mono stays the strongest mode" says; every deck of one set pays the same, so best fit within a request does not move, and a commander's colors are not a choice.
- **For a theme**: its pool margin over the floors (full at `grow.marginFull`), its richness over plain bulk of the same colors (the smaller of setup and payoff, each in the measure its floor counts, capped at `grow.richnessCap`), its depth (each side left at its bare floor costs `picker.depthWeight`, nothing at `picker.depthFull` times the floor), the commander's lead when it pays the theme off (`grow.commanderPlan`), all divided by `picker.themeMargin`, so a theme ranks above a plain shape only by that clear margin. Richness is a ratio of counts, and plain bulk reads up to about 1.3 to 1.8 in a color by chance, so a side counts above 1 only beyond its own noise: minus `picker.richnessZ` (1.65) over the square root of the theme cards plain bulk of these colors would hold, never below 1. A tribe the commander names takes the commander's lead.

The score is rounded to `picker.scoreStep` (0.01), below which the parts do not tell decks apart, and plans that tie go to Midrange, then Aggro, then Control, then the themes by id (`planOrder`); the options and the Analyze pane break ties the same way. Best fit's notes name the plans it compared in order; the scores stay internal (`explanation.pick`). A request where the grow builder can fill no plan and the classic builder no shape gets the classic builder's own best fit.

## Build options (phase 11)

The Build page has settings on the left and deck options on the right.

- **Settings**, in this order: deck size (100, 60, 40, 20), rarities (a drop-down with a checkbox for common, uncommon, rare, and mythic, all on by default), max copies per card (held at 1 for 100), infinite basics, colors (one or more), primary archetype, and secondary archetype. Both archetype choices are drop-downs that default to best fit. The primary list comes from the scan's `rules` (a theme Viable, or Short with what the pool lacks, down to `grow.nearMargin` of the floors, both pickable; a plain shape Viable wherever the size can be built); the secondary archetype unlocks once a primary archetype is picked and lists only archetypes that can be supported alongside it, from the scan.
- **Options**: cards on the right, as many columns as fit (three on a 1920-pixel window), one per deck option: title and description, a color wheel with each color's share of the colored mana symbols, the mana curve, copies of each card type, role coverage, and mana notes. A score ranks the options but is never shown. Without a secondary style it is the plan picker's score, the one best fit ranks by, plus a bonus for an option built for every picked color, as best fit is (`buildOptions.allColorsBonus`), so the first option is `buildDeck`'s best fit for the same request, card for card, and the options that drop a color follow. With a secondary style it is the classic deck score plus the bonus for a deck whose spells use every picked color (and, from phase 12, for meeting the secondary style).
- **Fit**: options stay inside the request but need not use all of it. Every option uses only picked colors (any non-empty subset). A picked primary style is required: every option is built for it (builds pass `requireStyle`, the player asked). Where the seed-and-grow builder takes the request (a themed style or a shape, no secondary) and the pool cannot support the style, the option is the nearest deck with a note saying what the pool lacks, shown on the card and in the deck view; where the classic builder takes it (a secondary style, a tribe), a style the pool falls short of fails instead of building another style, and when no deck can be built the right side says that no decks meet the settings, with the lacks sentence when there is one, and offers a Clear settings button (inline, not a popup). The secondary style is best effort, and an option that could not meet it is marked as such. An option that uses everything picked ranks above an equally strong one that drops something. Styles and colors that were not picked never appear.
- **Plans**: with no style picked and no secondary style, each color subset plans what best fit compares there: the themes the rules call viable, the three plain shapes (always, so a Commander deck opened from the Analyze pane never lands on an empty list), and under a commander the tribes it names. The set of every picked color is planned in full first, so best fit is always among the options, and the smaller sets take turns with what is left of `buildOptions.maxBuilds`. A plan the pool cannot fill is dropped. With a secondary style, each subset plans the styles the scan calls viable, one from each subset in turn.
- **Generation**: options are ideas, each built from the full pool, so one option's cards stay available to the next. They build one at a time in a Web Worker, as the Analyze pane's search does (`deckOptionSearch` in `packages/core/src/options.ts`, on a pack of only the pool's cards and basics), so the page never stalls on a build, and appear as they finish, re-sorted by rank, with a progress indicator while work remains. Scans of each color subset are kept while the size, build settings, and pool stay, so changing colors or archetypes plans at once. Builds take turns across the color subsets, so smaller color sets get built too. The count is capped in config, an option that shares most of its cards with a stronger one is dropped (at 100 only one of the same style, since a commander's plans share most of the 99), and without a picked primary style at most two options share a style. Opening an option or leaving the Build screen pauses the work; returning resumes it. Settings and finished options survive moving between screens.
- **Commander (100)**: singleton is forced. The right side first lists commander candidates from the pool by tier, as card-shaped tiles (four across on a 1920-pixel window): the card's text laid out like a card, or its image when card art is on, with the deck it leads, the pool cards in its colors, and its mana below. Picking one keeps it in a pane on the right, card and details, with a red Change Commander button the size of Accept and Back, and options build beside it; Change Commander returns to the commander list. The build settings stay editable while a commander is picked: changing any of them (colors, rarities, infinite basics, either archetype) returns to the commander list with the new setting, as Change Commander does.
  - **Colors** filter the list before a commander is picked: a commander shows when all its colors are picked (none picked shows every one), and the ones that use every picked color come first in each group. Each color button counts the commanders with that color. Once a commander is picked, the buttons show its colors; toggling one returns to the list with the colors on screen, plus or minus that one, as the filter. Change Commander, or any other setting, brings back the colors picked before.
  - **Primary archetype** also works before a commander is picked. Its choices are the styles the listed commanders lead (a synergy style the theme rules give their own text a payoff or setup job for, or a tribe it names; Aggro, Midrange, and Control suit every commander), viable when the pool can build it under some leader (each commander's own scan, the commander counted as the builder counts it) and short when none can (still pickable, to see who leads it). A commander's listed leads are the viable themes its text pays off where the pool pays for its needs, its feeds the ones it is setup for. Picking one keeps the commanders that lead it and groups them as Can build, Checking, and Not enough cards. A commander under whom the pool cannot build the style (its own scan's `rules`; a tribe by its member and payoff counts) goes straight to Not enough cards; the rest get a full build in the background, one per browser tick and best first, and move up or down as each finishes (`commanderCanBuild`: the deck comes back as the style and not as a nearest deck; a classic deck must also meet its enabler and payoff minimums). Checks are kept until the pool or settings change and pause while a commander is picked.
  - Picked colors and styles stay when a commander is picked, changed, or accepted, and when switching between 100 and the other sizes; styles picked before the commander lead its options. With a commander picked, the archetype pickers offer the commander list's choices, since picking one returns to that list.

## Analyze pane (phase 14)

The blue Analyze button on the Bulk List (it glows softly while the pane is closed) opens the pane under the list. It shows what the pool can build and what it holds. The web app has it; the phone layout still shows the per-color archetype table, each style's line the pool's counts against the rules' floors as the builder counts them ("12 setup cards · 6 payoff cards").

- **Recommended decks**: the strongest decks found so far for Commander, 60, 40, and 20, five each, picked from the whole pool (two decks can share cards). Max colors per deck (one to five, two by default, under the heading on the left) filters them; the deck score can rate four and five-color decks as fully castable, so without the limit many-color decks crowd out the ones that play best. Each row shows only the deck's colors and name, centered in a row tall enough for a name on two lines; a spinner by the heading shows the search is still going, and each column counts its checks. The score is not shown. Picking one opens it on the Build page like any deck option, with the form set to its size, colors, and commander, best fit, and the stored copy limit, so Back lands on options like it.
- **Search** (`bestDeckSearch` in `packages/core/src/best-decks.ts`): at 60, 40, and 20 it scans every color set and plans what best fit compares there (the themes the rules call viable and the three plain shapes; each color set's most promising style first, then each one's next, fewer colors first in each turn); at 100 it builds best fit under every commander with enough cards for the 99. Results are ranked like deck options with no picked colors (no all-colors bonus), by the plan picker's score, at most two per style, near copies dropped, except that each commander keeps its deck since commanders of the same colors draw on the same cards. Every color limit keeps its own ranked list, so changing the limit is instant.
- **Background**: the search runs in a Web Worker while the pane shows, so the Bulk List never stalls on a build (a Commander build takes up to a second). Each size gets equal time, one scan or build per step. The worker gets only the pool's cards and the basic lands (`poolPack`), which build the same decks as the full pack. Closing the pane or leaving the Bulk List pauses it; results are kept until the pool or the build settings change, which starts over. A 3,000-card five-color list checked about 1,500 decks in about 75 seconds on desktop while the 20-card packets were still classic (they took half of it; a grow best fit at 20 builds in about 40 ms, against 110 ms before), with the first decks showing within one or two seconds.
- **Breakdown** (`poolStats`), all in copies, in this order:
  - **Colors**: a pie of every card by color class (the five colors, colorless, and multicolor, from color identity) with each one's share and count under it, then a second pie, always shown, with each multicolor card counted in every one of its colors.
  - **Mana value by color**: spells by color class and mana value (0 through 6 or more) as a shaded table with totals. Clicking color rows picks them (several at once, with a blue outline); bars under the table chart the picked colors, or every spell when none is picked (clicking All clears the picks), each bar with its mana value and count under it.
  - **Card types**, **Roles by color** (the builder's roles), **Creature types** (as printed, changelings included), and **Subtypes** (of noncreature, nonland faces, such as Aura, Equipment, and Vehicle), each as a shaded table by color class. Card types counts lands; the others count spells, so their columns are the colors with spells. Roles end with "\* not all roles presented here"; creature types and subtypes list the twelve largest and, when there are more, end with "\* not all creature types presented" or "\* not all subtypes presented".
  - Rarity, sets, and prices are left out: they do not change which deck to build.

## Commander (phase 13)

- **Legality**: the commander must be allowed by the format (a legendary creature card, Vehicle, or Spacecraft with power and toughness, or text that says it can be your commander; partner and background pairs later). Cards banned or not legal in Commander stay out of the commander list and the 99. Every card fits inside the commander's color identity. Singleton except basics and cards whose text allows more.
- **Candidates and tiers**: top, good, and possible (see `docs/guides/commander.md`), ranked by how many pool cards fit its identity, whether its own text rewards a style the pool supports or a creature type it holds, its mana value, and its colors against the fixing in the pool. Game Changers are allowed; bulk rarely holds many. Partner and Background pairs and colorless commanders are not supported yet.
- **Template**: 35 to 40 lands (38 to start), 8 ramp, 12 card advantage (draw, cantrips, and looting), 8 removal, 3 sweepers, 4 finishers, and the rest for the theme, so lands plus ramp land near 45 to 47, as in the official precons. Every Commander deck uses the `commander` curve profile. The commander counts as one card toward each role it fills, so the deck still works when it is off the table. Numbers live in `deck-templates.json` and the `commander` block of `builder-weights.json`; the reasoning is in `docs/guides/commander.md`.

## Jumpstart packets

A 20-card packet includes its lands (about 8) and is built so that any two packets of different colors shuffle into a playable 40-card deck: a lower curve, a self-contained theme, no cards that need the other color. Packets always use the template's `jumpstart` curve profile, whatever the archetype. The Decks screen pairs two saved packets and exports the combined list.

Since builder phase 2 step 5 the grow builder builds every packet without a secondary style, best fit, options, and the Analyze pane ranked by the plan picker as at the other sizes, and the scan's `rules` list the styles. A spell is a candidate only when the packet can cast it once shuffled with another (`halfCast` in the 20-card template, `halfCastable` in `candidates.ts`): played as half of a 40-card deck with 16 lands, its own 8 lands, split evenly among its colors, the only sources of its colors, it needs 0.3 chance to have seen its mana value in lands, and its pips in the share of its own lands of the colors that can pay them (a hybrid pip either color's), by turn 10 on the play; a split, adventure, or modal card counts by its cheapest face, a prototype card by its cheaper cost. So in a one-color packet every spell of mana value 7 or less stays but five pips of one color, or four on a seven-drop, and every spell of mana value 8 or more goes (a ten-mana Eldrazi was dead in half of the review prototype's 20-card builds). The theme rules count no payoff at 20 that counts a resource or waits for a threshold, and Spellslinger's packet floor asks for 4 setup with its 3 payoffs, so a packet's theme works from its own cards (rules version 8, `docs/review/theme-rules.md`).

## Evaluation

- Fixed test pools in `eval/pools/`, each exercising something specific.
- A written rubric in `eval/rubric.md`: curve, type mix, role coverage, synergy, mana base, playability.
- `npm run eval` builds every pool at every size and color the scan allows, plus best fit under the two most promising commanders of each pool (`--commanders <n>` changes the count), scores the decks with automatic metrics (size and copy invariants, land count against the formula clamp, curve deviation, type mix, role coverage, synergy density, filler, castability, build time), writes `eval/results/<date>-<sha>.json`, prints a summary per pool and per size, and shows per-size deltas against the previous full run. It exits 1 on any build failure or broken invariant. `npm run eval:pools` regenerates the synthetic pools from a fixed seed. An on-demand GitHub Actions workflow runs the same suite.
- Committed baselines in `eval/results/` are full best-fit runs, one for each change that moved the numbers: `2026-11-03-fe5b028.json` (schema 1 pack, margin-based best fit), `2026-11-04-74cbcae.json` (schema 2 pack, card strength and best fit by building), then one per phase after that. `2026-11-04-4e1817a.json` added the Commander runs; `2026-11-05-87ed03d.json` is the learned plan choice of phase 3 of `docs/learned-builder.md`, `2026-11-05-46ecf28.json` the learned card selection of phase 4, and `2026-11-05-0830853.json` the learned deck score of phase 5 (its deck score column is on the new scale at 100, 60, and 20), the latest. Compare new runs with the latest.
- Claude reviews decks against the rubric as a development aid, not as ground truth. The user calibrates on a sample.
- **Reference corpus** (developer side, nothing committed or shipped): `npm run corpus:fetch` collects official preconstructed decks (Commander, 60-card, and Jumpstart) and, with `--drafts <sets>`, Arena draft decks with their game records, plus the owner's local lists with `--local <dir>`, into `data/corpus/`. `npm run corpus:eval` shuffles each reference deck into a seeded random bulk list, builds at the deck's size (under its commander at 100, otherwise in the colors its spells' pips ask for, so a hybrid card does not add its second color), and reports per size how much of the deck the build used, whether it picked a style the deck meets, its shape against the reference, and whether our deck score rates the reference's own build at least as high as ours. One deck in five is held out as a test split, so config tuned on the rest can be checked against decks it never saw. `npm run corpus:learn` writes `data/corpus/report.md`: deck shapes next to our templates, card tags that crowd around commander tags, theme coverage, card traits against bulk, and what goes with winning in draft. The report suggests; config changes stay a reviewed decision.

## Architecture

npm workspaces monorepo, TypeScript throughout.

| Package               | Role                                                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `@bulk-brew/core`     | Types, decklist parser, name resolution, pool, scan, builder, export. Pure, unit-tested, no DOM or Node APIs.               |
| `@bulk-brew/ui`       | Shared React pieces and hooks: storage, pack and config loading, pool, decks, settings, build flow, card detail, deck view. |
| `@bulk-brew/pipeline` | Developer-side data pipeline.                                                                                               |
| `@bulk-brew/web`      | Desktop-first React app. Static build deployed to GitHub Pages.                                                             |
| `@bulk-brew/mobile`   | Phone and tablet React app. Wrapped by Capacitor for iOS.                                                                   |

- **Storage**: pool, decks, and settings in IndexedDB behind one key-value interface (`packages/ui/src/storage/kv.ts`). On iOS the same store runs in the WebView unless phase 8 moves it to native storage. Backup is a JSON file export and import; restore writes the restored keys in one transaction.
- **Offline**: the web app is an installable progressive web app. Its service worker precaches the app shell and built assets per deploy and keeps the data pack in a separate cache that survives deploys. The iOS app bundles everything.
- **iOS**: Capacitor wraps the mobile app's static build. Builds run on the user's Mac mini with Xcode and ship through TestFlight and the App Store. The home-screen icon comes in a light and a dark version (`apps/mobile/resources/`), matching the web app's icon, which follows light and dark mode in the sidebar and the browser tab.

## Compliance

- Scryfall data is free for Magic software. Credit Scryfall, never paywall its data, never imply endorsement, and add value beyond repackaging.
- Wizards' Fan Content Policy governs card names, text, and images. Both apps carry the Fan Content notice on their About screen. See `ATTRIBUTION.md`.
- Scryfall API requests carry a descriptive User-Agent and Accept header where the platform allows it, and are spaced at least 100 ms apart. Bulk files are fetched at most daily.
- Image and data requests go from the user's device, never through a developer server.
- 17Lands public draft data (CC BY 4.0) and MTGJSON's preconstructed deck lists (MIT) tune the builder through developer-side scripts. Both are credited and thanked on the About screen of both apps and in `ATTRIBUTION.md`; no deck data from either ships.
- EDHREC is read developer-side by `npm run edhrec:fetch`: one request per second with a named User-Agent, every answer cached under `data/edhrec/` (gitignored) and refetched at most weekly. Only derived, rounded numbers reach the apps. Commander Spellbook's bulk file, made for third parties, is downloaded at most weekly; the apps carry each combo's cards, results, bracket tag, legality, and variant id. Both are credited on the About screens and in `ATTRIBUTION.md`.

## Decisions

Resolved questions, kept so they are not reopened by accident.

- Core language: TypeScript. UI: React 19, Vite, Tailwind. Tests: Vitest. Package manager: npm.
- iOS: a separate mobile interface on the shared core, wrapped by Capacitor. Not a Swift port, not a responsive single app.
- Database: JSON data pack, not SQLite.
- Data distribution: release assets plus a pinned manifest, not committed packs.
- Rulings: never bundled.
- Pools: one active pool. Multiple named pools are not planned.
- Deleting a deck: offers to return its cards to the pool. A committed deck records `basicsTaken` when basics were tracked at commit time, so the return does not depend on the current setting.
- Copy limits: 4 for 60 and 40, 2 for 20, adjustable. 100 is singleton, not adjustable.
- Un-set cards: excluded by default, toggle in settings.
- Land count: formula from curve and cheap mana sources, not a fixed number.
- Colors: one to five colors in every size; mono stays the strongest mode; more colors are allowed even though they build worse. Packet pairing stays.
- Deckbuilding guidance from outside material is restated in our own words in `docs/guides/` and config, with no source names in the repo.
- Reference decks for tuning come from sources that allow automated download: MTGJSON's preconstructed decks (MIT) and 17lands' public draft data. Their names appear in the corpus fetch script and in the credits (the About screen and `ATTRIBUTION.md`), as Scryfall's do. Sites whose terms forbid automated access are not used, with one exception the owner decided on 2026-11-05: EDHREC, fetched developer-side at a gentle rate for learning in this personal, non-commercial, open-source project, credited with the other sources, with only derived numbers reaching the app. Commander Spellbook asks only for credit. Config learns numbers from the corpus; no third-party deck data ships in the app.
- Game Changers are not filtered out.
- The app says archetype where the code and config say style (`style`, `secondary`, styleBonus). Labels can change freely; ids stay, so saved decks and eval results keep working.
- Finisher means a card that can end a Commander game at 40 life: an overrun, an extra combat, another way to win, a planeswalker costing five or more, a creature with seven or more power, an evasive or trampling one with five or more, or an evasive double striker. Only the 100-card template asks for finishers. The 60, 40, and 20-card templates ask for big threats (big bodies, big flyers, planeswalkers), the role id `finisher` kept so saved decks still read.
- Deck scores stay internal: no strength number on screen or in builder notes, since raw scores invite the wrong comparisons. The score rewards strong cards together, which is not the same as a deck that works, so it is a ranking aid that keeps being reworked, not a measure of power.
- The deck list groups cards by exact type (creatures, planeswalkers, instants, sorceries, artifacts, enchantments, battles, lands), the same groups the Card types breakdown counts. A Commander deck lists its commander first in a group of its own; Card types still counts it under its type.
- Tribal is a secondary style, except under a commander whose own text names the tribe (its Tagger `typal-<type>` tag), where the tribe can be the primary style with twice the secondary counts (28 members and 4 type payoffs at 100). A secondary style needs a primary style; a second theme needs half its minimums, a shape can only follow a themed primary, and a tribe needs members and type payoffs (`builderWeights.secondary`).
- Styles are kept: learned deck plans (`docs/learned-builder.md`) add styles beside the hand-written ones, never replace them. The Build page only shows styles the pool can build, so a longer list costs nothing.
- Name: Bulk Brew, repo `bulk-brew`. An unrelated dormant repo shares the name; not a concern.
- Result actions: Accept (green), Back (red), and Export (grey). Export, there and on Decks, asks in a popup as Remove does: Copy as text, Download .txt, or Cancel. Accept asks Confirm and remove the cards from the bulk list, Confirm and keep them there, or Decline, stacked in that order. A kept deck (`committed: false`) shows "Cards in bulk list" on Decks and can be accepted later to remove them. Choosing Build in the sidebar while a built deck is open works like Back.
- Short display tags live in `config/display-tags.json`, matched with the same matcher format as roles plus role and style references. They are for showing and filtering only; the builder never reads them, so they are not part of the config version a deck records.
- Pairing packets is a what-if view from a packet; Merge replaces both packets with one 40-card deck. Basics return on disassembly only if both packets took them.
- Appearance lives in `localStorage`, outside `Settings` and backups, so no settings format changed.
- The Analyze pane's deck search and the Build page's deck options each run in a Web Worker on a pack of only the pool's cards and basics. The Commander list's archetype checks still build on the main thread, one per tick.
- Card detail in a deck view (a fresh build, a saved deck, a packet pairing) opens over the deck details, below the deck's header, so Accept, Back, and Export stay in view; a click on any header button closes it. The Bulk List keeps its own panel.
- Replace (web, a fresh build only): the card detail's Replace button lists cards from the pool that fit the deck with the build's colors, copy limit, and settings, spells for a spell and nonbasic lands for a land, the closest matches first: the jobs they share with the card going out (the roles the deck counts and its theme sides, as the Roles bars count them), then card strength, mana value, and creature or not; lands by the land rules (`packages/core/src/replace.ts`). A job counts only when earned: the outgoing card's in the deck now, an option's in the deck after the swap. A basic land is a valid replacement for a nonbasic land (owner's decision, 2026-11-16): the basic of each deck color the land makes (every deck color for a land that makes none), ranked by the land rules, so in a one-color deck it comes before any land worse than it; with basics tracked, only the pool's basics beyond those the deck runs. Taking it raises the deck's basics and moves its colored sources; since basics have no line of their own, a builder note says which nonbasic it replaced. The picked card shows large beside the list, or over it on a narrow window until Back to the list. A swap takes as many copies as the pool has spare, within the builder's usual copies of legendary and expensive cards, labels the new card "Swapped in for" the old one, and brings the explanation's curve, roles, land notes, and synergies up to date; the deck score is dropped. The ranking weights are constants in that file, not config: they only order a list the player picks from, and the builder never reads them. Saved decks are not edited.
- Near miss is a display label only: not viable, the size is buildable, and at most 3 cards short in total (`NEAR_MISS_SHORTFALL` in `packages/ui/src/data/analysis.ts`). The builder never reads it.
- Plain-language card tags are the config's role labels and style (archetype) labels, not raw Scryfall tags; the raw tags stay behind a disclosure.
- The theme rules are a config file (`config/theme-rules.json`) that may read oracle text and type lines with regular expressions; a card counts once, as setup or as payoff, and a rider counts as nothing. Owner decision, 2026-11-11.
- One set of definitions (builder phase 2, step 4): everything the grow builder serves, and everything the player sees of it (the scan's viable styles and counts, the style pickers, the commander list's leads, the Roles bars, reasons, Replace's jobs, key synergies, and card tags), reads the theme rules, counted as the builder counts them. The matchers in `archetypes.json` stay only for the classic builder's paths (secondary styles, tribes), whose decks show what that builder counted; step 7 removes what nothing reads then.
- A requested style the pool cannot support gets a note that says what the pool lacks in plain words and then the nearest deck that can be built, labelled for what it is: never a best fit in disguise and never a bare error. `requireStyle` on a request means the player asked for the style. Owner decision, 2026-11-11.
- Best fit means the best deck. There is no target mix of styles; Aggro and Midrange being common from bulk is fine, and the other viable styles stay in the Build page's list below the first option. Owner decision, 2026-11-11.
- Speed is not a goal in itself. A build must stay well short of minutes; slower than that means a bad algorithm. Owner decision, 2026-11-11.
- The commander counts once toward a theme job, as the rules count it; the prototype's three-fold credit was dropped.
- A card gets credit for a job (a role, a theme job, strength, a land's utility, its place in a deck) only in a deck that supplies what that job depends on, for every card and every kind of dependency. An automated reader decides it from the card's rules text, which is strict and templated; the vocabulary and templates are config, the parsing is code, and it runs over every new set with no one in the loop. Agents do not tag cards, and no per-card data is written by hand except the few stubborn cards in `config/tag-overlay.json`. Owner decision, 2026-11-16.
- One plan picker (builder phase 2, step 3): at 60, 40, and 100 cards one score ranks the finished deck of every plan (the three plain shapes, the themes the rules call viable, and a commander's tribes), so best fit, the Build page's first option, and the Analyze pane agree, and the first option is best fit card for card. A theme must beat the best plain shape by `picker.themeMargin`, not by richness noise. Learned plan data is retired for every grow path and every plan best fit compares, a commander's tribes included (owner decision, 2026-11-16), and stays only for the classic secondary styles. Since step 5 the picker ranks 20-card packets the same way, built by the grow builder; secondary styles and tribes keep the classic builder.
- 20-card packets (builder phase 2, step 5): a packet is half of a 40-card deck, so a spell it cannot cast there is no candidate (`halfCast` in the 20-card template), and the theme rules count no payoff that counts a resource or waits for a threshold at 20 (rules version 8), as the theme guide's 20-card rows say.
- Builder changes ship on a blind panel of agents judging held-out pools (`docs/review/judging.md`), never on the builder's own counts. Theme counts from the rules are never evidence that a builder is better.
